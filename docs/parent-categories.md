# Parent category administration

`GET /api/v1/admin/parent-categories` lists shared root categories with `id`, `label`, `child_count`, `assignment_count`, and `can_delete`.

`POST` on the same endpoint accepts `action` (`add`, `rename`, `delete`), string `id` for rename/delete, and `label` for add/rename. Names are trimmed, required, limited to 120 characters, and checked against other parent names using the database collation. IDs, slugs, artwork, and existing assignments survive renames.

Both operations require an enabled application administrator. Household ownership alone grants no access. Changes affect the catalog used by every household. No schema migration is required.

New parents automatically receive an AI-generated square cover using the existing server-only recipe AI configuration. Generation runs after category creation commits; an image-provider failure preserves the category and returns a `cover_warning`. `POST /api/v1/admin/parent-categories/{id}/category-image` retries a missing cover. It requires an enabled application administrator, accepts an empty JSON object, and returns `image_url`. The list includes `image_key`, `image_url`, and `needs_ai_image` for previews and retry controls. Existing bundled covers and AI files are preserved; renaming does not regenerate artwork. AI covers are generated once under a per-category lock and shared with every household. Household image-generation permissions still apply to ordinary recipe/subcategory image requests; administrators manage this global parent artwork separately.

The reviewed `bin/cover-homemade-ingredients.php` backfill is CLI-only and restricted to the verified coffeybean.com directory and dedicated recipe database. It selects exactly one parent named “homemade ingrediants” or “homemade ingredients”, preserves its name and recipes, saves the original category metadata in protected storage, and generates only its missing cover. `tool/cover-homemade-ingredients.py` schedules the temporary CLI job, removes that exact cron command in a finally block, and verifies the public image against the protected SHA-256 receipt. The Ubuntu deployment workflow can run it with `homemade_ingredients_cover` or the explicit `[homemade-ingredients-cover]` commit marker; routine deployments do not backfill other categories.

Deletion requires no child categories and no direct recipe assignments in any household, including assignments belonging to recently deleted recipes. Even an empty child prevents deleting its parent. Parent-row locks and existing foreign keys protect against concurrent assignments/child creation. Nonempty deletion returns 409 without removing data.

Validation: `php tests/parent_categories.php` runs 49 isolated in-memory checks for authorization, disabled accounts, add/rename/delete, validation, duplicates, child protection, assignments from another household, automatic cover generation, retry without duplicate AI calls, lock contention, existing-cover preservation, failure recovery, and unchanged household child-image permissions. It does not access a persistent database and does not model MySQL locking. Existing photo tests (30 checks) and recipe deletion fixtures (40 checks) pass. Five one-time-job tests cover credential gating, receipt validation, public hash verification, destination restrictions, and cron cleanup after success/failure.
