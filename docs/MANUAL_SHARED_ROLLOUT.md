- **Engine gate:** MariaDB **10.4.32** and **10.11.19** have been rehearsed for this helper. Hosted preflight on 2026-10-16 confirmed **10.11.19-MariaDB**. Any other hosted engine/version deliberately stops before maintenance/migration. Rehearse that exact engine in a disposable environment and review compatibility before extending the gate. Do not bypass it merely to deploy.
- PHP requires PDO MySQL, mbstring, ZipArchive, and permission to inspect `crontab -l` and `ps -eo args`. All tables must be InnoDB with primary keys; triggers, routines, events, and views require an expanded backup plan and are rejected. Earlier migration ledger checksums must match, including the existing explicit migration-008 compatibility rule.
- Provide an explicitly provisioned, **empty**, dedicated `<account>_recipes_recovery_<8 lowercase hex digits>` database on the same host. Its creation/access requires verified hosting authority. The helper never creates or drops hosted databases. The recovery copy is retained.
- The CLI credential needs SELECT/INSERT and schema privileges needed by the reviewed SQL (CREATE, ALTER, REFERENCES) on the dedicated recipe/recovery databases. If needed, use `ROLLOUT_DB_USER` / `ROLLOUT_DB_PASSWORD` in the temporary process environment. First record existing privileges privately; restore and verify them before reopening service. No automatic privilege changes or credential persistence occur.
- Inventory all CLI/background writers. The helper can check the known purge process/cron, not arbitrary external writers. The operator must confirm those are stopped and API maintenance actually returns 503. The 300-second drain is a minimum, not proof that an unbounded import/job ended.

## Failure and recovery

The helper never removes maintenance on failure, never drops a hosted schema, never replaces live data with a dump, and never automatically retries a partially applied DDL sequence. A failed command's outcome is determined by `state.json`, `ddl-started.json`, actual schema and migration ledger—not by the exit code alone. The database may already have committed some DDL.

Before DDL, a verified unchanged original backend/database can be restored to service by a reviewed operator recovery: validate original source/media archive, restore the original `.htaccess` if necessary, and restore the saved purge schedule. Do not remove maintenance without checking whether DDL actually started.

After DDL begins, keep maintenance and purge paused. Inspect the last completed statements and ledger; prepare a forward repair against a fresh disposable copy. Do not delete the journal or rerun ALTER statements to “try again.” The retained empty-database restore drill already produced a verified pre-migration recovery copy. If forward recovery is impossible, a separately reviewed cutover can pair that recovery schema with the original verified backend archive. Such a cutover must reconcile any post-snapshot writes and explicitly authorize configuration changes; it is not performed by this tool. Reverting PHP alone is unsafe. No down-migration is supplied or claimed reversible.

The dump is UTF-8 JSON Lines containing individual SQL statements; it deliberately avoids splitting data on semicolons. `SharedRecipeRollout::restoreDrill` verifies its digest and executes statements only into a different, empty database, then compares restored inventories. Do not feed this file directly to the mysql SQL client. Keep backups private.
